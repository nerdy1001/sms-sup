# FN-06: Staff front-end shell: layout, routing, English and French, accessible components

Status: Complete (2026-11-05)
Milestone: M1-A
Estimate in the plan: not recorded here

## What was asked

The task of the delivery plan, as you gave it on 2026-11-05: **"Staff front-end shell: layout, routing,
English and French, accessible components"**. The scope was built before the entry was seen and was compared
with it afterwards:

| Part of the entry | Where it is |
|---|---|
| Layout | `src/layout/shell.tsx`: skip link, header, navigation, main area. |
| Routing | `src/app.tsx` with react-router: home, sign-in, a page for unknown addresses. |
| English and French | `src/i18n/` (i18next), with a language switch in the header. |
| Accessible components | `src/ui/` (button, field, alert) and the shell: labelled fields with linked error text (`aria-invalid`, `aria-describedby`), alerts with the right role, visible focus, `aria-pressed` on the language switch, a labelled navigation, the `lang` attribute kept in step with the language. |

Beyond the entry, and kept small: a typed API client, the repository rules for browser code, and the
staging image and routing. Decisions made when it started:

| Question | Decision |
|---|---|
| Stack | Vite and React, built to static files. |
| Installing packages | Done on your computer and sent back as `deps.zip` (the build environment has no registry access). |

## What was built

| Part | What it is |
|---|---|
| `apps/staff-web` | The application: shell, routing, home page with a live readiness check, placeholder sign-in page, not-found page. |
| `src/api/client.ts` | The typed API client (timeout, schema check, RFC 9457 problem handling). |
| `src/i18n/` | i18next with an English and French catalogue, typed so a missing text fails the build; API error codes map to messages. |
| `src/ui/` | Button, field and alert components. |
| `tools/checks/web.ts` | New repository rules for browser code (docs/boundaries.md). |
| `apps/staff-web/Dockerfile`, `Caddyfile` | The static image. |
| `infra/staging/` | Compose service `staff-web`; Caddy sends API addresses to the API and the rest to the front end, with a strict content policy. |
| `.github/workflows/ci.yml` | Builds both images into one tar for the deploy. |
| `package.json`, `tsconfig.json` | `npm run typecheck` and `npm test` now include the front end. |

## How to check it

    npm run check                                      # types, rules, 580 Node tests and 45 front end tests
    npm run dev                                        # the API (terminal 1)
    npm run dev --workspace @minesup/staff-web         # the page (terminal 2), then open http://127.0.0.1:5173

Verified in the build environment: types, rules, all tests, `vite build`. Verified on your computer
(2026-11-05): both Docker images build (the front end image needed one fix, the missing `tsconfig.base.json`),
the front end image starts and serves the page, and the page works in a browser against the local API.
**Not verified:** the staging serving (the Caddy routing between the API and the front end, and the
content security policy) on a real server, because the staging server does not exist yet (FN-03). That check
belongs to the FN-03 runbook.

## Not included and known gaps

- Real sign-in (AC-01). The sign-in page is a placeholder that shows the shape of the error handling.
- Business screens; each module task adds its own.
- Accessibility is built into the components and the shell (list above) and covered by tests of labels, roles and focus order where they apply, but it has not been audited with a screen reader or an automated tool such as axe. That audit is worth doing before real users arrive.
