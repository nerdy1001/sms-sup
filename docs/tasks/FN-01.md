# FN-01: Repository, coding standards, module boundary checks

Status: Complete (2026-10-26)
Milestone: M1-A
Estimate in the plan: 2 days

## What was asked

Task FN-01 of the delivery plan: set up the repository, the coding standards and the checks that keep
the module boundaries intact. Decisions made when it started:

- The code is owned by you and lives in a private GitHub repository.
- You are the only developer.
- Node.js and TypeScript, with the best ideas of NestJS but without NestJS itself (the learning curve is
  not affordable now). The earlier authentication code will be rewritten inside the new structure.
- Delivery as an archive. Continuous checks on GitHub Actions.

## What was built

A repository that contains no feature yet, but has everything that keeps features from going wrong.

| Part | What it is |
|---|---|
| `apps/core-api`, `apps/portal-api` | Empty shells of the two programs (staff application and student portal API), each with a `kernel/` and a `modules/` folder and a README. |
| `packages/contracts` | The only code both zones may share, for data shapes. |
| `tools/` | The checks (imports, structure, sql, standards, docs), the module generator, the pull request title check and 129 tests of all of them. |
| `docs/` | The guide, the progress log, the task records, the rule reference, the module map, three decision records and the GitHub settings checklist. |
| `.github/` | The workflow that runs the checks on every pull request, the pull request checklist and the weekly update proposals. |
| Root files | `package.json` with three workspaces and two development dependencies, strict TypeScript settings, `.npmrc` (exact versions, no install scripts), `.nvmrc`, editor and Git settings. |

## How it works

1. **Structure.** Each application has a `kernel` (toolbox) and `modules` (business features). Every
   module has the same files and the same four layers (`http`, `application`, `infrastructure`,
   `domain`). See [the modules page](../guide/03-modules.md).
2. **The robot.** `npm run check:rules` reads all the source files with the TypeScript parser, extracts
   the imports, strings and comments, and compares them with the rules in `tools/rules.config.ts`.
   The rules are listed in [boundaries.md](../boundaries.md). See [the checks page](../guide/04-checks.md).
3. **The generator.** `npm run new:module -- RG` creates a module in the standard shape, but only for
   a code that is in the plan.
4. **The gate.** The GitHub workflow runs the type check, the rules and the tests on every pull request
   and also checks that the pull request title looks like `feat(rg): add scholar identifier`. With the
   branch settings in [github-setup.md](../github-setup.md), a red check blocks the merge.

The rules that matter most:

- The portal and the staff application can never import each other.
- A module can only use another module through its public file, and only if it declared the dependency.
- The domain and application layers use no library and no Node module.
- Network code exists only in a few named places, so the staff application can only call out.
- A module touches only its own database schema.

## Why it was done this way

- **One repository:** [ADR 0001](../adr/0001-one-repository.md). One developer, two zones separated by
  rules and by deployment, not by repository.
- **No framework, with its ideas:** [ADR 0002](../adr/0002-node-and-typescript-without-a-framework.md).
- **Checks written for this project instead of ESLint, Prettier and dependency-cruiser:**
  [ADR 0003](../adr/0003-architecture-rules-as-code.md). The environment that built this had no access
  to the npm registry, so those tools could not be installed or tested. The checks use the TypeScript
  parser, which was already needed. The cost is about 1,500 lines of project code, all tested.
- **Turborepo not used:** it speeds up builds across many packages and does not enforce module rules.
  It can be added later without changing the structure, when the front ends exist and CI time grows.
- **Minimal workflow only:** the full pipeline (dependency audit, static and secret scans) was delivered
  in [FN-02](FN-02.md).

## How to check it

From the repository root, with Node 22.18 or later:

```
npm install        # first time: creates package-lock.json, then commit it
npm run check      # type check, rules, tests
```

Expected: no errors, no warnings, all tests passing (129 tests). The same result was obtained from a
fresh copy and from the unpacked archive. The first delivery had 116 tests; the documentation check added
afterwards (see [the documentation index](../README.md)) brought the total to 129.

To see the robot work, break a rule on purpose, for example create a file in
`apps/portal-api/src/kernel` that imports from `apps/core-api`, and run `npm run check:rules`. It
reports `zone-isolation` with an explanation. Delete the file again.

The tests were also checked for strength: five rules were disabled one at a time in a throwaway copy and
the matching tests failed each time.

## Not included and known gaps

Not part of FN-01 and handled by later tasks:

- Dependency audit, static analysis and secret scanning: FN-02 (delivered, see [its record](FN-02.md)).
- Staging environment: FN-03. Database and row-level security: FN-04. Configuration, logging, errors,
  web server and API contract: FN-05. Staff front end: FN-06.

Known gaps:

- **No `package-lock.json`.** The registry was unreachable, so no lock file could be generated.
  *Resolved on 2026-10-26: the lock file was generated and committed, and `npm ci` succeeded on GitHub.*
- **Node types are newer than Node.** `@types/node` is pinned to 26.6.3 (the version tested) while
  `.nvmrc` selects Node 22, so the compiler may accept an API that only exists in newer Node.
- **The workflow has not run on GitHub.** The commands it calls were run and tested; the workflow file
  itself was not.
  *Resolved on 2026-10-26: the `checks` job ran and passed on GitHub. The `pr-title` job was skipped on a
  push, as designed, because it runs only for pull requests.*
- **No general linter or formatter.** Adding ESLint with typescript-eslint, and Prettier, is the sensible
  next step on a machine with registry access.
- **Windows was not tested.** The tools build paths carefully, but nothing was run there.
- **SQL built from several concatenated pieces cannot be seen by the SQL check.** The query helper of FN-04
  is meant to close that gap.
