## How it works

`npm run lint` reads every `.ts` and `.tsx` file with the type information of the compiler and reports
mistakes. `npm run format` rewrites the files into one layout; `npm run format:check` fails if any file is
not in that layout. ESLint never argues about layout, because `eslint-config-prettier` turns those rules off.
The repository checks (`npm run check:rules`) keep their own job: architecture, security and standards.

## What ESLint found, and what was done

| Finding | Count | Action |
|---|---|---|
| Promise from `test()` or `describe()` not awaited | 480 | Not a defect: the rule was told about `node:test`. |
| An `async` function with nothing to wait for | 8 | Not a defect: the rule is off (reason above). |
| Type assertion that changes nothing | 5 | Removed (automatic). |
| A template that would print a `Secret` | 2 | Left on purpose: the test checks exactly that. Two `eslint-disable` lines with the reason. |
| State set synchronously inside an effect (`home.tsx`) | 1 | Rewritten: the page is "checking" whenever the stored answer belongs to an earlier round. Same behaviour, tests unchanged. |
| An object that could print as `[object Object]` | 2 | Made explicit (`tools/audit.ts`, `tools/db/connection.ts`). |
| A rethrown error without its cause | 1 | The cause is attached (`tools/db/connection.ts`). |
| A value assigned and never used | 1 | Removed (`tools/lib/modules.ts`). |
| A type-only constant seen as unused | 1 | Exported (`UI_KEYS`). |
| A method used as a loose function in a test | 1 | `Project.write` is declared as a function property. |

## Why it was done this way

- **Strict from the start.** Starting soft and tightening later means a second round of fixes. The 22 real
  findings were small enough to fix in this task.
- **Width 140.** It is close to how the code was already written, which kept the reformat to layout changes
  that the code did not already have.
- **Prettier for `.ts` and `.tsx` only.** The documents are written by hand and read as text, so a formatter
  would only add noise to them.
- **ESLint does not repeat the repository checks.** Two tools that report the same thing in different words
  are worse than one.

## How to check it

    npm run lint            # no output means no findings
    npm run format:check    # all files use the Prettier code style
    npm run check           # everything

Verified in the build environment: all three, with 580 Node tests and 53 front end tests passing.
`pino-pretty` could not be tested against the real library there, so run `npm run dev` once and look at the logs.

## Not included and known gaps

- Markdown, JSON, CSS and YAML are not formatted by Prettier (only `.ts` and `.tsx`), so the documents keep their hand-made layout.
- ESLint has no rule about architecture or security; those stay in `tools/checks`.
- ESLint runs in about 25 seconds because of the type information. If that becomes a nuisance, the type-aware rules can be limited to CI.
