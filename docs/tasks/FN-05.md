## What was asked

Task FN-05 of the delivery plan: the skeleton that every module of the staff application will stand on. A
way to read and check configuration, a way to write logs that never leak personal data, one format for
errors, a web server with a described API, and the database driver that makes the row-level security of
FN-04 usable. The decisions made when it started:

| Question | Decision |
|---|---|
| Libraries or Node by hand | Libraries, now. Manage complexity before it grows. Every library is justified in a register. |
| Web framework | Fastify, after comparing it with Express (section 2 below). |
| API description | Keep an OpenAPI document, generated from the route definitions. |
| Error format | A stable code and an English message for developers, in the standard problem details format. The front end translates by code. |
| Scope | The staff application (`core-api`) only. The portal skeleton comes with the portal tasks and reuses `packages/contracts`. |
| Dependency register | Confirmed: `docs/dependencies.md`, enforced by a check. |
| Installing libraries | Done on your computer, then sent back as `deps.zip`, because the environment that builds this cannot reach the package registry. |

You also asked for a review of the places where an npm package could replace code written by hand against
Node. It is section 3. And you asked that every decision be explained here, so section 2 is the longest
part of this record.

## How it works

**Start.** `main.ts` reads the environment through `loadConfig`. If anything is wrong it prints the list
of problems (names of variables, never values) and exits with code 1. Otherwise it creates the logger,
calls `startApplication`, and installs handlers: a termination signal stops the application cleanly
(finish the requests in progress, then close the database connections, with a ten second limit), and a bug
that nobody caught is logged safely and ends the process so the platform restarts it.

**A request.** In order:

1. Fastify reads the request and gives it an identifier (`x-request-id`; the proxy's value is kept only
   when it is short and made of harmless characters).
2. The `onRequest` hook adds the identifier and `cache-control: no-store` to the answer. Then, for a route
   that is not public, it asks the authenticator who is calling. No identity gives 401, a role that is not
   in the route's list gives 403. This happens before the body is read or checked.
3. The rate limit counts the request (300 per minute per address; `/health` and `/ready` are not counted).
4. The body, parameters and query string are checked against the route's zod schema. A failure is a 400
   with the position and kind of each problem and never the value.
5. The handler runs. To touch data it calls `database.asUser(identity, work)`, which opens a transaction in
   which the policies of FN-04 see the staff member.
6. The answer is checked against the route's response schema. Fields the schema does not list are removed,
   and an answer that does not fit is a bug (500), never sent.
7. One log line is written: method, the route as written (`/api/scholars/:id`, never the real address),
   status and duration.

**An error.** Anything thrown reaches one handler (`failure.ts`). An `AppError` keeps its code and its
sentence. Input that does not match becomes `validation_failed`. Framework errors (unreadable JSON, a body
over 1 MiB, a content type that is not JSON, the rate limit) get their own codes. Everything else is a bug:
the caller gets `internal_error` with no detail, and the log gets the type of the error, its code and its
stack, but not its message (see "Logging" in section 2).

**The API description.** `npm run api:docs` builds the application without starting it, asks Fastify for the
OpenAPI document, and writes `docs/api/openapi.json`. Every operation lists who may call it (`x-access`)
and the standard error answer. A test fails, and so does `npm run check`, if the file is out of date.

**Adding a route** is described step by step, with an example, in
[the guide](../guide/06-writing-a-route.md).

## Why it was done this way

### 1. Libraries now, and a register to keep them honest

You asked to manage complexity before it grows. The skeleton is where hand-written code would grow fastest:
an HTTP server, request validation, logging with redaction, security headers, a rate limiter and a
database pool are all things that are short to write badly and long to write well. Each one was weighed
(section 3). Eleven libraries are now direct dependencies, all pinned to an exact version, and each has a
row in `docs/dependencies.md` with four answers: what it is for, why it was not written by hand, what we do
if it is abandoned, and where in the code it may be imported. The `register` check fails when a library has
no row, a row is incomplete, a row does not list the workspace that declares the library, or a row remains
after the library was removed (a warning).

The honest cost: eleven libraries bring 69 packages into `node_modules` and one more thing for Dependabot to
update. Libraries that are written and maintained by one person are the biggest risk. The register names
the one case among the eleven (`fastify-type-provider-zod`) and its fallback.

### 2. The decisions, one at a time

**Fastify, not Express.** Both would work. The reasons for Fastify, in order of weight:

- It checks input and output against a schema as part of the framework. With Express that is a separate
  layer that has to be chosen, written and kept in step with the routes. Here the same zod definition checks
  the request, types the handler, checks the answer, and describes the route in the API document.
- It strips from an answer every field the schema does not list. For a system that holds identity numbers and
  bank details, an extra field cannot leak by accident (there is a test for this).
- It uses Pino, the logger chosen below, natively, and it gives each request a child logger with its identifier.
- Its plugins are encapsulated: a plugin registered for one part of the application does not touch the rest.
  That matches the idea of a module, which ADR 0002 already expected.
- It runs under Node 22 without a build step, like the rest of the repository.

The reasons against, so the choice is not a one-sided story: Express has the larger ecosystem and more
people know it; Fastify changes more from one minor version to the next (two options that I used were
already deprecated in the version installed, and the code uses the replacements). The pinned versions and
Dependabot are the answer to that. The decision is recorded in [ADR 0007](../adr/0007-web-framework-and-libraries.md).

**zod as the one definition of a shape.** Settings, requests, answers and the shared contracts are all zod
schemas. Version 4 is used (the one installed is 4.6.7). A shape is written once and gives the check, the
TypeScript type and the API description. `packages/contracts` may use zod (the architecture rule already
allowed it) and nothing else.

**Contracts hold the error codes and the problem shape.** The list of codes and the shape of an error
answer are in `packages/contracts`, not in the staff application, because the portal will answer in the same
way and the front ends of both zones need the same list to translate. What each code means over HTTP (its
status and title) stays in the application. The contracts package now also lets its own test files use
`node:test` and `node:assert`; its other Node restrictions are unchanged. That is a change to an architecture
rule (`contracts-purity`), made because a package without tests would be the one thing in the repository
that nothing checks.

**Errors: a stable code, an English sentence, no values.** The answer follows RFC 9457 (problem details) and
is sent as `application/problem+json`. The fields are `type` (`urn:sms:error:<code>`), `title`, `status`,
`code`, `detail` (only for errors raised on purpose), `requestId` and, for invalid input, `errors`, a list
of `{ path, code }`. The code is the contract: the front end shows French or English text chosen by code, and
tests check the code. The sentence is for developers. Two rules matter more than the format:

- **No value is ever repeated.** Invalid input is reported by position and kind (`body.count`,
  `invalid_type`), not by what was sent. A person who types a national identity number into the wrong field
  does not see it echoed, logged or cached. A test sends a recognisable value and checks that it appears
  nowhere in the answer.
- **A bug says nothing.** The text of an unexpected error can contain a query, a path or personal data, so
  the caller gets `internal_error` and the request identifier, which is enough for you to find the log line.

**Logging: JSON lines, and the first rule is to log little.** Pino writes one JSON object per line to
standard output, with the level as a word, the time in UTC, the service name and the version. What is
logged and what is not:

- A request line holds the method, the **route as written**, the status and the duration. It never holds the
  real address (identifiers and names can be in it), the query string, the headers or the body.
- A caught error is described by `errorFields`: its type, its code and its stack (without the first line,
  which is the message). The **message is written only when its source is known to be safe**: errors raised
  on purpose, errors of the web framework, and errors of the language itself. The message of a database
  error repeats the values of the query (for example the e-mail address that was already taken), so it is
  left out and the SQL state code (such as 23505) says what happened. A plain `Error` does not get its
  message written either, because the code that threw it might have put data in it. That makes unexpected
  errors harder to read, and the stack is what you read instead. If it proves too strict it can be loosened
  in one place.
- **Redaction is the second line of defence, not the first.** Fields named `password`, `token`, `email`,
  `phone`, `firstName`, `dateOfBirth`, `iban` and about twenty more (in camelCase, snake_case and kebab-case)
  are replaced by `[redacted]` up to four levels down, in case someone logs an object by mistake. A field with
  another name is not caught, which is why the first rule exists.
- Health checks are logged at debug level only, because they run every few seconds.

**Configuration.** The environment is read in two places only (`kernel/config` and `main.ts`, enforced by the
`no-process-env` rule). The settings are checked by one zod schema at start. When something is wrong the
application lists every problem at once, naming variables and never printing values, so one run shows
everything to fix. Specific choices:

- Defaults exist only for `local` and `test`. The database settings point at the container of `npm run
  db:up`. In `staging` and `production` the database host and the password file are required, so a forgotten
  variable stops the start instead of pointing the application at the wrong place.
- **Secrets are files, not variables.** The password is given as `DATABASE_PASSWORD_FILE`, the path of a file.
  A secret in an environment variable shows up in process listings, in crash reports and in `docker
  inspect`. The loader refuses `DATABASE_PASSWORD` and `DB_PASSWORD` outright, with a message that says why.
  Inside the application the value is wrapped in `Secret`, which prints as `[redacted]` in a log, a JSON
  dump or a debugger; only `database.ts` calls `reveal()`.
- An empty variable counts as missing, so a stray `PORT=` cannot become port 0.
- `TRUST_PROXY` (`true` or `false`, default `false`) says whether to believe the client address that the
  reverse proxy reports. Staging sets it to `true` because Caddy is the only container that can reach the
  application; without it every request would appear to come from Caddy and share one rate limit.

**Who may call a route: declared, never assumed.** Every route has to carry `config: { access: "public" }`
or `config: { access: ["role", ...] }`. A route without it makes the application refuse to start and name the
route, so a protection cannot be forgotten by leaving a line out (several wrong forms are tested). Until the
sign-in task AC-01 exists, the authenticator rejects everyone, so every route that is not public answers
401. There is **no development login and no shared test password**: a login that works in development is
one configuration mistake away from working in production. A test that needs a signed-in user supplies its
own authenticator, inside the test file. The check happens in `onRequest`, before the body is read and
validated, so a stranger learns nothing about the shape of the input.

**Two health questions.** `/health` says the program is running and never touches the database, so a
database outage does not make the platform restart a program that works (the deploy script and the container
health check use it, and the answer still contains `"version":"<commit>"` as the deploy script expects).
`/ready` asks the database and answers 503 with the code `unavailable` when it does not answer. Both are
public, say nothing about the data, and are not rate limited.

**Defences in the web layer.** Each is small, and each has a test:

- Security headers on every answer (Helmet), with a content security policy that allows nothing, because an
  API never serves a page. `cache-control: no-store` on every answer, because answers hold personal data.
- Only `application/json` bodies are read. Fastify also reads `text/plain` by default, and a web page of
  another site can send `text/plain` across origins without any permission check, which is how cross-site
  request forgery is attempted. With JSON only, the browser must ask first. Other content types get 415.
- A body larger than 1 MiB is refused (413) and a request that takes more than 30 seconds is cut. Document
  uploads (module DM) will need their own larger limit on their own route.
- A body that tries to change an object's prototype (`__proto__`) is refused; this is Fastify's default and
  it is tested.
- A rate limit of 300 requests per minute per address. It is a coarse protection for the whole application;
  sign-in (AC-01) will add a much stricter limit on its own route.
- No CORS headers. The staff front end and the API are served from the same origin through the reverse
  proxy, so none are needed, and the `cors-open` rule would reject an open setting anyway.

**The database adapter.** `pg` is the driver, and only `kernel/db` imports it (the `database-driver` rule).
The pool holds at most 10 connections, waits at most 5 seconds for one, and the server cancels any query
that runs longer than 15 seconds. `asUser(identity, work)` borrows one connection, runs `runAs` from FN-04
on it, and returns it, so one request always uses one connection and one transaction and the identity cannot
carry over. `withoutIdentity` exists for the few functions that must run before sign-in; with no identity
the policies show nothing, so it is of no use for ordinary queries. One real defect was found by a test
while building this: a connection that dies while a request is using it (a database restart) produces an
error event with no listener, which in Node ends the whole program. The adapter now listens while it holds a
connection, logs the failure and discards the connection. The test kills the backend in the middle of a
request and checks that the next 15 requests are served.

**OpenAPI: kept, and why.** The staff front end could import the zod shapes directly and get the same
types, so for the front end alone the document is not needed. It is kept because other readers exist: the
banks and auditors who will ask what the system sends and receives, and anyone who builds an integration,
cannot import a TypeScript package. The document costs one library (`@fastify/swagger`), one generated file
that is reviewed like code, and a test. It is built from the same route definitions that serve requests, so
it cannot say something the code does not do. Two additions go beyond the standard output: `x-access` on every
operation (who may call it), and the standard error answer on every operation. A small oddity: zod writes the
limits of a whole number as plus or minus 9007199254740991 in the document. It is correct (the largest safe
integer) and harmless.

**`npm run dev`.** It runs `node --watch` on the real entry point with `SMS_ENV=local`, through the small
program `tools/dev.ts`. The program exists because setting an environment variable differs by system
(`SMS_ENV=local node ...` does not work in PowerShell), and it keeps development running the same program as
staging. The logs in development are JSON lines, which are hard to read. A reader such as `pino-pretty` would
fix that, at the cost of one more library; it was not added without asking (see "What comes next").

**The image installs from the lock file.** The Dockerfile now runs `npm ci --omit=dev` for the core
workspace, so the image holds exactly the versions that the tests ran with, and it sets `HOST=0.0.0.0` (inside
a container the program must listen on all addresses; Compose binds the published ports to the Tailscale
address). `SMS_ENV` and the database settings come from `infra/staging/compose.yaml`, never from the image.

**Scope.** Only `core-api`. The portal needs the same skeleton with different exposure rules; it is built
when the portal tasks start, and it reuses `packages/contracts`. Building both now would have doubled the
review for a part that has no routes yet.

## How to check it

Without a database, or with one: `npm run check`. In the environment that built this, with a real
PostgreSQL, it reports 0 errors, 0 warnings and 518 tests passing.

On your computer, with Docker running:

```
npm run db:up
npm run db:migrate
npm run dev
```

Then open `http://127.0.0.1:3000/health` (answers `{"status":"ok","service":"core-api","version":"dev"}`)
and `http://127.0.0.1:3000/ready` (answers `{"status":"ready"}`). Stop `npm run db:up` with `npm run db:down`
and reload `/ready`: it answers 503 with the code `unavailable`, and `/health` still answers 200. Any other
address, for example `/api/anything`, answers 404 in the problem format. Stop the application with Ctrl+C: it
logs `The application is stopping.` and exits.

To run the database tests on your computer: `npm run db:up` and, in PowerShell,
`$env:SMS_TEST_DB_MODE="docker"; npm test`. The tests of the staging scripts are skipped on Windows and run
on GitHub.

What was tested here, with the real packages installed from your `deps.zip`:

- The web layer, 36 tests that send requests through the whole application without a network: health and
  readiness; the headers; request identifiers (a harmless one kept, four hostile ones replaced); 404 and 405;
  an error raised on purpose, a bug (message absent from the answer and the log), and an answer that does not
  match its schema; invalid input (position and kind, the value never repeated, unknown fields, query
  string, broken JSON, wrong content type, oversized body, `__proto__`); the access rules (a forgotten
  declaration, an empty or malformed one, several methods, no identity, wrong role, right role, check before
  validation); the rate limit and the proxy address; and what the log does and does not contain.
- The application as a whole, started on a real port against a real PostgreSQL: `/health`, `/ready` with the
  database up and down, a 404, a clean stop that closes the port, and a port already in use.
- `main.ts` as a real process: a wrong configuration exits with code 1 and a list of problems, a correct
  one starts, answers and exits with code 0 on SIGTERM. `npm run dev` was started and stopped with Ctrl+C.
- The database adapter against a real PostgreSQL as the `sms_app` role: identities, rollback, commit,
  parameters, the identity not leaking between uses, 40 requests on 10 connections, an unreachable
  server, and a connection killed in the middle of a request.
- The logger (11 tests), the error mapping (12), the configuration (18), the contracts (4), the register
  check (9), the API description (4).
- Fourteen deliberate breakages of the code were tried, one at a time (removing the access check, the
  JSON-only rule, the redaction, the identity setting, the connection listener and so on), and each should
  make a test fail. Thirteen did. One survived: discarding a connection after it fails is also done by the
  pool, so a test cannot tell the second line of defence from the first. It is kept because it costs nothing.

## Not included and known gaps

Not part of FN-05: sign-in, sessions and roles (AC-01); the audit hooks (FN-07); encryption (FN-09); the staff
front end (FN-06); the portal skeleton; log shipping and metrics; secrets management for production (FN-10).

Known gaps, in order of importance:

- **The Docker image build is unverified.** The `Dockerfile` now runs `npm ci`, and this environment has no
  Docker and cannot reach the package registry. I checked what I could: `npm ci --dry-run --offline` with the
  same files plans the install from the lock file without complaint. The first real build is the pipeline on
  GitHub (`ci.yml` builds the image). If that job fails, send me the log.
- **Staging reaching its database is built but unproven.** Since 2026-11-04 the deployment runs the migrations
  and sets the password of `sms_app` (ADR 0005, decision 10; FN-04 follow-up). `/ready` on staging should answer
  200 after the first deployment; no server has run it yet.
- **`405` is only found for fixed paths.** A request with the wrong method to `/health` gets 405 and an
  `Allow` list; the same mistake on a path with a parameter (`/api/scholars/7`) gets 404. Fixing it needs a
  look inside the router; it matters little for an internal API.
- **The strict error messages make unexpected errors harder to read** (see "Logging"). The stack is kept.
- **Fastify writes one line of its own at start** (`Server listening at ...`) in addition to ours. It holds only
  the address and is harmless, and it was left in.
- **No metrics and no tracing.** The request identifier and the log line are all there is for now.
- **Readable logs in development need one command from you.** `npm run dev` now pipes the output through
  `pino-pretty` when that library is installed, and prints plain JSON when it is not. I could not install it
  here (no access to the package registry), so run `npm install --save-dev pino-pretty` and add its row to
  `docs/dependencies.md` (see the guide, "Readable logs"). The piping was tested with a stand-in program; the
  real library was not.
- **A service in front of the application is assumed** for TLS (Caddy in staging). The application itself speaks
  plain HTTP, and sets a strict-transport header that only matters behind that proxy.
- **`fastify-type-provider-zod` has a single maintainer.** The register names the fallback. Version 7 supports
  Fastify 5 and zod 4, which is why those versions were chosen.
- **I was not able to run `npm run dev` on Windows.** It uses only `node:child_process` and plain arguments, but
  please run it once and tell me what you see.
