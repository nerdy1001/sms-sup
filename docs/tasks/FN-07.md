# FN-07: Audit hooks for writes and reads

Status: Complete (2026-11-05)

## What was asked

The delivery plan entry, as you gave it: **"Audit hooks for writes and reads"**. The audit table existed
since FN-04 and nothing wrote to it. Decisions made when it started:

| Question | Decision |
|---|---|
| Which reads are recorded | Declared sensitive reads: a route that shows personal data says so. Not every read. |
| Refused attempts | Recorded in the audit log when a signed-in person is refused (wrong role). Requests with nobody signed in stay in the application log only. |
| How a write cannot happen without its entry | The kernel writes the entry in the same transaction as the change, from the route's declaration. |

## How it works

A route that changes data says what it does, in its configuration, next to who may call it:

    config: { access: ["attache"], audit: { action: "scholar.suspend", objectType: "scholar" } }

and does its work through `request.transaction`. That function opens one transaction as the signed-in person,
runs the work, then writes the entry in the same transaction and commits. If anything fails, everything is
rolled back, the change and the entry together. The handler tells the kernel which records it touched with
`audit.object(id)`. A read of personal data does the same with an action such as `scholar.read`. Details are
in [guide 6](../guide/06-writing-a-route.md), "Routes that change data, and the audit log".

Three things stop mistakes early:

1. A route that changes data and is not public, with no declared action: the application does not start.
2. A declared action that was not recorded when the route answers with success: the answer is replaced by an
   error and the log names the action.
3. A detail that holds personal data (a key such as `email` or `phone_number`, or a value that looks like an
   e-mail address): the request fails and nothing is kept.

## Why it was done this way

See [ADR 0009](../adr/0009-audit-hooks.md). The main reason for writing the entry inside the kernel: a
forgotten call would be a silent gap in a log that cannot be corrected afterwards.

## How to check it

    npm run check          # 624 Node tests, including the audit ones, and 53 front end tests

The tests against a real PostgreSQL run when a database is available (`npm run db:up` and
`SMS_TEST_DB_MODE=docker` on Windows). They show an entry in the name of the person who asked, the change
and its entry disappearing together when the work fails, a refused attempt recorded in the name of the person
refused, and that person being unable to read the log.

Mutation checks done by hand: removing the guard, removing the entry write, or removing the record of
refusals each made the tests fail.

## Not included and known gaps

- No route uses the hooks yet, because no module has routes. The first module task will be the first user,
  and will show whether the interface is comfortable.
- A GET route that changes data through `database.asUser` is not detected. It is a rule of review: a GET
  does not change data.
- Which reads count as "personal data" is decided per route in each module task.
- Failed sign-ins and password resets happen before anyone is signed in. They are for AC-01 and need entries
  without an actor from the session.
- A screen for auditors to read the log, filters, retention and archiving are not part of this task.
