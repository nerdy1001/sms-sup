# FN-04: PostgreSQL, migrations, row-level security, seed data

Status: Complete (2026-10-28)
Milestone: M1-A
Estimate in the plan: 3 days

## What was asked

Task FN-04 of the delivery plan: a database for the staff application, with a way to change it in
controlled steps (migrations), a security model in which the database itself refuses access to rows the
caller may not see (row-level security), and synthetic data to develop with. Decisions made when it
started:

| Question | Decision |
|---|---|
| Migration tooling | Plain numbered SQL files and a small runner of our own. No ORM for now (see ADR 0006). |
| What the policies separate | The staff member's role and, for the portal later, the scholar's own identity. |
| Seed data | Synthetic only, repeatable, 200 scholars from a fixed seed. |
| Which tables now | The platform schema only: migration history, staff users, audit log. Business tables belong to their modules (for example RG-01). |
| PostgreSQL version | 17, as in the local and staging containers. |
| Local development | The existing local Compose database, plus commands to migrate, seed and reset. |

One adaptation of those answers: 200 synthetic scholars were agreed, but a scholar table belongs to the
registry module (RG-01), so FN-04 builds the generator and its tests and leaves the rows for RG-01. What
FN-04 actually seeds are four synthetic staff members, one per role.

## How it works

**Migrations.** `npm run db:migrate` finds every `.sql` file under a `migrations` folder (the kernel's
first, then each module's by name, each in number order), asks the database which ones it has already
applied, and applies the rest. Each file runs inside one transaction together with the row that records
it (name and a SHA-256 fingerprint of its content), so a migration either happens completely and is
recorded, or leaves no trace. If a file that was applied has changed, or the database knows a migration
that no file explains, the runner stops and says so. It talks to PostgreSQL through the `pg` driver, using
the usual `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE` and `PGPASSWORD` settings (default: the local container
on `127.0.0.1:5432`). *Changed on 2026-11-04: it sent scripts to the `psql` command until then; see the
follow-up at the end of this record.*

**Who is asking.** The application connects as the role `sms_app`. Before running a request's queries it
calls `runAs`, which opens a transaction and sets `app.user_id` and `app.role` for that transaction only.
The policies read those settings. Without them nothing is visible and nothing can be written.

**What the policies say.**

| Table | Read | Write |
|---|---|---|
| `platform.users` | Your own row; an administrator reads all | Administrators only |
| `platform.audit_log` | Auditors and administrators | Anyone may add an entry in their own name; nobody may change or delete one |

**Seeds.** `npm run db:seed` runs the files in the `seeds` folders, each in a transaction. They are
written to be repeatable (`on conflict do nothing`), which a check enforces. It refuses to run when
`SMS_ENV` is anything but `local`, `staging` or `test`. `npm run db:reset` drops the local database,
migrates and seeds, and refuses outside a disposable setup.

**The checks.** `npm run check` now also reads every SQL file: tables must have row-level security
enabled and forced, files must be numbered without gaps, no `begin` or `commit`, no `grant ... to
public`, security definer functions must fix their search path, seeds must be repeatable, and platform
migrations may touch only the platform schema. See [boundaries](../boundaries.md).

Concepts are in the [glossary](../guide/glossary.md); the folders are in the
[repository tour](../guide/02-repository-tour.md).

## Why it was done this way

The reasons and the alternatives, including why Prisma was not chosen, are in
[ADR 0006](../adr/0006-database-design.md). In short: the policies are the security of the system and
need hand-written SQL whatever tool is used; a runner of our own adds little code on top of the driver the application already uses;
and a check that a table cannot exist without its policies is cheaper than remembering to write them.

## How to check it

Without a database: `npm run check`. It runs 414 tests and the rules; the only warning is
`lockfile-missing` in a copy without a lock file.

With your local database:

```
npm run db:up
npm run db:migrate      # Applied 3 migration(s).
npm run db:seed
npm run db:status       # 3 applied, 0 pending.
npm run db:migrate      # Nothing to apply
```

Then follow the runbook's "How the database knows who is asking" and see the policies refuse and allow.
To run the database tests against your container, set `SMS_TEST_DB_MODE=docker` and run `npm test`
([runbook](../runbooks/local-database.md)).

What was tested here, against a real PostgreSQL 16: the three migrations and their policies (20 tests
that connect as `sms_app`, including no identity, wrong identity, malformed identity, promotion attempts,
spoofed audit entries and tampering with the audit log); the runner (applying, repeating, edited and
missing files, a failing migration rolling back, module order, seeds twice); the command line end to end;
the ten check rules (27 tests); the generator (7 tests). Ten deliberate breakages of the policies were
tried; nine were caught, and the tenth (a looser `with check` on the update policy) changes nothing
because the `using` clause already restricts the same rows.

## Not included and known gaps

Not part of FN-04: business tables and their policies (each module's own tasks, starting with RG-01 and
AC-01); the portal database, which is a separate zone and a separate task; the database driver and
connection pool in the application (FN-05); secrets and roles for production (FN-10, FN-11); backups of
the local database (staging has them, see FN-03).

Known gaps, in order of importance:

- **Developed against PostgreSQL 16, targeted at 17.** The environment that built this had 16. Nothing
  used is specific to 17, but the first run on your container is the real check. If a test fails there,
  send me the output.
- **The Docker route has now run (2026-10-28).** It was not run when this task was built, because the
  daemon was missing here. On your Windows computer, `npm run db:up` and then the tests with
  `SMS_TEST_DB_MODE=docker` passed every database test: migrations, row-level security, the audit log and
  the seeds, against the PostgreSQL 17 container.
- **The CI step that installs PostgreSQL has not run on GitHub.** The tests are made to fail there, not
  skip, if no PostgreSQL is found, so a problem shows up on the first run instead of hiding.
- **Staging migrates on deployment (added 2026-11-04), but has never run.** See the follow-up below.
- **The staff roles are provisional.** `administrator`, `attache`, `finance_officer` and `auditor` are
  placeholders chosen from the Ministry interviews. Task AC-01 owns the real list and replaces them.
- **How `sms_app` logs in is not decided.** It is created without a password. Locally the database trusts
  connections from your computer. Staging and production must set a password or another method outside
  the migrations (FN-10).
- **The seed runs as the owner and works only because the local owner is a superuser.** A non-superuser
  owner is blocked by `force row level security`. That matters when seeds run on staging with a stricter
  role split.
- **The audit log has no tamper-evident chain.** It cannot be changed through the application and the
  trigger stops the owner, but someone with full control of the server could drop the trigger. A hash
  chain belongs to the audit module (AU).
- **The `users` table has no password, MFA or session fields.** Authentication is AC-01.
- **The checks read statements, not a full SQL parser.** They catch the usual layouts and can be fooled by
  unusual ones, such as a table created inside a function.

## Follow-up (2026-11-04): the runner uses `pg`, and staging migrates

Two changes made after the task was accepted, both agreed with you:

- **`psql` is gone from the tools.** `tools/db/connection.ts` now uses `pg`. The functions became
  asynchronous (`await migrate(...)`). Scripts of several statements still run in one session and one
  transaction where they did before; the only statement pair that had to be split is dropping and creating a
  database, which PostgreSQL refuses to run as one script. A Windows computer needs Docker for the container
  but no longer needs `psql` at all. `SMS_DB_MODE` was removed; `PGHOST` and the other standard variables
  replace it. `SMS_TEST_DB_MODE=docker` still works and now means "use `127.0.0.1:5432`".
- **A new command, `provision`.** It migrates and then gives the application role `sms_app` its password
  from the file named by `APP_PASSWORD_FILE`. The statement is built by PostgreSQL (`format('%L')`), so the
  password is never spliced into SQL by our own code and is never printed. The deployment of staging runs it
  from the application image (ADR 0005, decision 10). The migrations themselves still create the role
  without a password.

What was tested: the whole suite passes (539 tests) against a real PostgreSQL 16, including new tests for
the password step and for the command line, and the command `provision` was run from a copy of the folder
layout of the image (only `tools/db`, one helper and `apps/core-api/src`), twice, against a real server.
What was not: the Docker image itself (the `COPY` lines and `.dockerignore` are unverified), and everything on
the real server.
