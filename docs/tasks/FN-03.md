## What was asked

Task FN-03 of the delivery plan: describe the staging environment of the core zone as code, so that it
can be created, deployed to, rolled back and rebuilt without remembering anything. Decisions made when
it started:

| Question | Decision |
|---|---|
| Where staging runs | One DigitalOcean droplet (Ubuntu 24.04, Frankfurt or another European region), paid by you. |
| Development | On your computer. The application runs directly with Node; an optional Compose file gives a local database and mail catcher. |
| Who can reach it | Only you, through Tailscale (free personal plan). No domain name. Nothing but SSH is open to the internet. |
| How it is deployed | Automatically after a merge to `main` once every check passes, over SSH, with a key that can only run the deploy script. |
| Registry | None. The image is built in the pipeline and sent as a file. |
| Rollback and backup | A rollback command; a nightly database backup kept 7 days on the same server, checked every night by a restore into a scratch database. |
| What runs on it | The core service (a placeholder with only a health endpoint when this task was built; the real application since FN-05), a PostgreSQL database and a mail catcher (Mailpit). |
| Secrets | One in GitHub (the deploy key). The database password is generated on the server. |
| Checks | New infrastructure rules added to `npm run check`. |

## How it works

**Setting up the server.** You paste `cloud-init.yaml` into the droplet creation page. On its first start
the server creates two users (`admin` for you, `deploy` for the pipeline), hardens SSH (keys only, no
root login), starts a firewall that allows only SSH and the Tailscale network, installs Docker and
Tailscale, and schedules the backup and its check. You then join the server to your Tailscale network and
run `init-staging.sh`, which creates the database password on the server. The runbook has every step.

**Deploying.** After a merge to `main`, once `checks`, `audit` and `secret-history` pass, the job
`deploy-staging` builds the image tagged with the commit, saves it as a file, and sends the image,
`compose.yaml` and `Caddyfile` over SSH. The server's SSH setting forces that key to run
`staging-deploy.sh` whatever the client asks, so the job can only deploy. The script then:

1. accepts only `deploy <40 hex characters>`, `rollback` or `status`;
2. takes a lock so two deployments cannot overlap;
3. accepts only an upload that holds exactly the three expected files, as plain files;
4. loads the image, checks that every other image exists, and starts the containers with Compose;
5. waits for the application to answer `/health` with the **commit that was sent** (so an old container
   that kept running cannot pass for the new one);
6. on any failure, goes back to the previous release and exits with an error, which fails the job and
   sends the Slack message;
7. keeps the last five releases.

**Who can reach what.** The server's public address answers only on SSH. The reverse proxy is bound to
the server's Tailscale address, so `https://<NAME>` works only from machines on your Tailscale network.
Caddy asks the local Tailscale for the certificate of the `.ts.net` name. The application and database sit
on networks with no internet access, so the application cannot call out and the mail catcher cannot send
real email. Containers run with no extra privileges, and the application's files are read-only.

**Backups.** `backup.sh` runs at 02:15 UTC and writes a database dump (a temporary name first, so a
half-written file is never taken for a backup). `restore.sh verify` runs at 02:45 and restores the newest
dump into a scratch database, counts the tables, and deletes the scratch database. A backup that is
never restored is a hope, not a backup.

**Local development.** Run the application with Node as before. `docker compose -f infra/local/compose.yaml
up -d` gives a database on `127.0.0.1:5432` and a mail catcher (SMTP on 1025, web page on 8025). It is
optional, and its settings are for a laptop only.

Concepts are in the [glossary](../guide/glossary.md) and the folder is described in the
[repository tour](../guide/02-repository-tour.md).

## Why it was done this way

The reasons and the alternatives are in [ADR 0005](../adr/0005-staging-environment.md). In short: one
server and Compose because one person must be able to keep it running; Tailscale because it keeps the core
off the internet as it will be in production, with no domain; a forced-command SSH key because it needs
no extra open port and no registry; ports bound to an address because Docker bypasses the server
firewall; and a health answer that carries the version because "the container is up" does not prove "the
new version is up".

## How to check it

On your computer:

    npm run check       # 331 tests; 0 errors
    node tools/check.ts --only infra

Expected: no errors. The only warning is `lockfile-missing` if you run it on a copy without the lock
file; your repository has one.

Then follow [the staging runbook](../runbooks/staging.md), parts A to E. The checks in part E are the real
acceptance test: the health address opens from your computer and not from outside, only SSH answers on the
public address, the deploy key refuses any other command, and the backup verification succeeds.

What was tested here: the check rules (35 tests, each rule with a passing and a failing case), the
deploy, backup and restore scripts (31 tests, run for real against a fake Docker and a fake Tailscale),
the health server (7 tests, and one live run), the Compose files with `docker compose config`, and the
server file (parsed as YAML, and its embedded scripts compared byte for byte with the sources). Nine
deliberate breakages of the scripts were all caught by the tests.

## Not included and known gaps

Not part of FN-03: the database, migrations and seed data (FN-04); the real application skeleton,
configuration and logging (FN-05); secrets management and zone separation for production (FN-10, FN-11);
the portal zone's environment; the production environment, which will be built differently (see ADR 0005).

Known gaps, in order of importance:

- **The server has not been created.** Creating it needs a payment card. Until it exists, nothing in this
  task has run on a real server.
- **Nothing has run on a real server.** This environment has no Docker daemon, no network and no
  server. The first deployment is the real test; expect to adjust something and send me the output of
  whatever fails.
- **The image tags were written from memory and are not verified:** `caddy:2.10.0-alpine`,
  `postgres:17.5-alpine`, `axllent/mailpit:v1.27.7`, `node:22.23.4-alpine`. The deploy script checks
  that they exist before changing anything, and the pipeline build will fail on a missing base image.
- **The Tailscale certificate path is unverified.** Caddy reaches Tailscale through its socket mounted into
  the container. If it does not work, the fallback in the runbook is `tailscale serve`.
- **The deploy key is root on staging.** Anyone who steals it can start any container on the server.
  Staging holds only synthetic data. This must not be copied to production.
- **Staging depends on Tailscale**, a third party, for access and for the certificate.
- **SSH is open to the internet** (keys only, limited attempts, a failed-login blocker). It could be
  closed too, at the price of making the pipeline join the private network.
- **The infrastructure checks read lines, not YAML.** They catch the mistakes listed in
  [boundaries](../boundaries.md) in the usual layout, and can be fooled by an unusual one.
- **Backups are on the same server.** A destroyed droplet loses them. That is acceptable for synthetic
  data; production needs a copy elsewhere (FN-12 or later).
- **GitHub approvals before a deploy** (Environments) may need a paid plan for private repositories, so
  none is required: a merge to `main` deploys.
- **The price is from memory:** about 12 US dollars a month for 1 vCPU and 2 GB. Check the page.
- **Changed by FN-05:** the service on staging is now the real application. The image installs its libraries
  from the lock file, and `infra/staging/compose.yaml` gives the service `SMS_ENV=staging`, the database
  settings and the password file. `/health` and the deployment are unchanged. None of this has run on a server.
- **Changed on 2026-11-04 (migration step):** each deployment now starts the database, takes a backup (not on the
  first deployment), runs the migrations from the new image as a one-off container (`migrate`, in the `tools`
  profile) and sets the password of the application role, all before the new version starts. There are now two
  database passwords (owner and application), both made by `init-staging.sh`; the running application can read
  only its own. A rollback does not migrate. The reasons and the rule for writing migrations are in ADR 0005,
  decision 10. The scripts were tested against the fake Docker (39 tests, 8 new); the real run is still pending
  the server.
- **Open from FN-02:** the audit against the real registry, the Dependabot merge and the Slack message
  are still unconfirmed.
