# FN-02: CI pipeline: tests, dependency, static and secret scans

Status: Complete (2026-10-27)
Milestone: M1-A
Estimate in the plan: 3 days

## What was asked

Task FN-02 of the delivery plan: extend the minimal workflow of FN-01 into a pipeline that runs the
tests and also scans for known vulnerable dependencies, for insecure code and for committed secrets.
Decisions made when it started:

| Question | Decision |
|---|---|
| GitHub plan | Free, private repository. |
| What blocks a merge | Secrets, and high or critical vulnerabilities in production dependencies. Everything else warns. |
| Accepted risks | Written in a file, each with a reason and an expiry date. |
| Dependabot | Merges by itself when every check passes. |
| Static analysis | One security-focused scanner, limited to rules that matter for a Node API. |
| Results on Slack | Yes, for failures on the main branch and in the daily audit. |
| Where it runs | GitHub-hosted runners. |

The lock file was already committed, and the FN-01 workflow had run on GitHub (the `checks` job passed).

## How it works

### The pipeline

Every pull request, and every push to `main`, starts these jobs in parallel:

| Job | Question it answers | Blocks? |
|---|---|---|
| `checks` | Do the types, the architecture and coding rules, the security rules, the secret scan of the files, the dependency rules and the tests all pass? | Yes |
| `audit` | Does a dependency have a known vulnerability that matters? | Yes, for high and critical in production |
| `secret-history` | Did a secret ever enter any commit? | Yes |
| `pr-title` | Does the pull request title follow the convention? (pull requests only) | Yes |
| `dependabot-merge` | Is this a safe Dependabot update that can merge now? (Dependabot only, after all four above passed) | Merges or leaves open |
| `notify` | Tell Slack. (pushes to `main`, only when a job failed) | No |

### The security rules (`security`)

| Rule | What it catches |
|---|---|
| `sql-interpolation` | A query text built from values with a template or `+`. Pass values as parameters. |
| `weak-hash` | MD4, MD5 or SHA-1 used as a hash. |
| `weak-cipher` | `createCipher`, or ECB, DES, RC2, RC4, Blowfish. |
| `dynamic-regexp` | `new RegExp(variable)`: a risk of freezing the server or changing what matches. |
| `tls-verification-off` | `rejectUnauthorized: false` or `NODE_TLS_REJECT_UNAUTHORIZED`. |
| `cookie-flags` | A cookie with `httpOnly: false` or `secure: false`. |
| `cors-open` | `origin: "*"` or `origin: true`. |
| `insecure-url` | A plain `http://` address outside the local machine. |

They run on application and package code (not tests, not `tools`). An exception is written as
`// security-ignore: <rule> -- <reason of at least 10 characters>` and appears in every report.

### The secret scan

It looks for private keys, AWS, GitHub, Slack, Google, Stripe and npm credentials, signed tokens (JWT),
passwords inside connection addresses, and values with high randomness assigned to names such as
`password`, `secret`, `token` or `apiKey`. Obvious placeholders (`password`, `${VAR}`, `<value>`,
`changeme`) are ignored. It also flags files that should never be committed: `.env` files (but not
`.env.example`), key and certificate files, and spreadsheets, database files and dumps, because those
can hold personal data of scholars. A report shows only the first four characters of a finding, never
the secret.

Two scans exist because they answer different questions. The working-tree scan runs inside
`npm run check` and tells you now. The history scan reads every added line of every commit on every
branch, so a secret that was committed and deleted again is still found, and the message says to rotate
it, because deleting a line does not remove it from the history.

A value that only looks like a secret (a documented example) can carry
`secrets-allow: <rule> -- <reason>` on its line or the line before. A hit in history is accepted by its
id in the risk file.

### Accepted risks

`security/accepted-risks.json` holds entries of the form:

```
{ "accepted": [ { "id": "GHSA-xxxx-xxxx-xxxx", "reason": "...at least 20 characters...", "expires": "2026-12-01" } ] }
```

An entry needs a reason of at least 20 characters, expires within 90 days, and stops counting on the
day it expires. An expired or malformed entry is itself an error, so the decision gets made again.

### The dependency audit

The audit runs `npm audit` twice, once for production dependencies only and once for everything. A
high or critical advisory in a production dependency blocks. A lower one, or any advisory in a
development tool, is printed as a warning. If npm cannot audit (no network, no lock file) the job fails,
because an audit that cannot run cannot vouch for anything. The audit also runs every day on its own,
because new advisories appear without any change to the code.

The dependency rules (`dependencies` check) add what the audit cannot see: every dependency has an exact
version, comes from the npm registry, and every locked package has an integrity hash.

### Dependabot

A pull request from Dependabot merges by itself only when all of these hold: every job above passed,
every update is a patch or a minor update, none of them is a minor update of a 0.x package (where a
minor release may break things), and the pull request changes only dependency files. Anything else stays
open for you. The merge happens inside the workflow, after the jobs, because GitHub's own automatic merge
depends on branch protection, which the free plan does not offer for private repositories.

### Slack

When a job fails on `main`, or the daily audit fails, `notify` posts a short message with a link to the
run. It needs a repository secret named `SLACK_WEBHOOK_URL`. Without it the step prints a note and
passes. The script refuses any address that is not a Slack webhook, so a mistyped secret cannot send the
message somewhere else.

## Why it was done this way

- **Written here, not downloaded.** The environment that built this could not reach the registries, so
  downloaded scanners could not be tested. The free plan also removes GitHub's own scanners for private
  repositories. [ADR 0004](../adr/0004-security-scanning-built-in.md) gives the full reasoning and the
  cost: the scans are less complete than the dedicated products.
- **The audit fails when it cannot run.** A quiet pass on a broken scan is the worst result.
- **Exceptions expire.** A permanent exception is a rule that has been switched off without saying so.
- **Dependabot merges patch and minor updates only.** A merge with no human review is acceptable for a
  small version change that passed every scan, and not for a major change. The five-day cooldown, exact
  version pins, `ignore-scripts` and the audit are the protections against a compromised release.
- **The history scan uses every branch.** A secret on an old branch is still a secret.

## How to check it

From the repository root:

```
npm run check            # types, all rules including security, secrets, dependencies, and the tests
npm run audit:deps       # needs network access to the npm registry and a lock file
npm run scan:secrets     # needs a git repository with its history
```

Expected: no errors; `check` also lists one warning only if the lock file is missing. The history scan
was run end to end in a temporary repository: it found a secret that had been committed and deleted,
found an `.env` file that had been added and removed, and passed on a clean history. The audit command
was run without registry access and failed with a clear message, as designed.

The tests were also checked for strength: seven rules or thresholds (the blocking level, the reason
length, the entropy limit, the major-update stop, the expiry check, the Slack address check and the SQL
rule) were broken one at a time and the tests failed each time. One survivor was found and closed by
adding a test.

To see the pipeline work on GitHub, push a branch and open a pull request. All four checking jobs run.
Then try a small mistake on purpose: add `export const o = { rejectUnauthorized: false };` to a file in
`apps/core-api/src/kernel`, and `checks` fails with `tls-verification-off`.

One-time GitHub steps are in [../github-setup.md](../github-setup.md): the Slack secret, the Actions
settings and the branch protection question below.

## Not included and known gaps

Not part of FN-02:

- Staging environment as code: FN-03. Database, row-level security, seed data: FN-04. Application
  skeleton, configuration, logging, errors: FN-05.
- A container image scan and an infrastructure-as-code scan: there is nothing to scan yet. They belong to
  FN-03 and FN-13.

Known gaps, in order of importance:

- **Only part of FN-02 has been seen running on GitHub.** The pipeline ran there and the task was
  accepted on 2026-10-27. Two problems were reported along the way: a type check failure in `checks`
  (TypeScript resolved to a different layout on the runner; the cause was not confirmed and the
  problem was reported as resolved) and an `audit-schedule` run that stayed at the post-checkout cleanup
  step (cause not confirmed). What has not been confirmed is the audit against the real registry, the
  Dependabot merge and the Slack message. The format of `npm audit --json` was written from its
  documented format (version 2) and tested with sample reports, not with a real one. Expect to adjust
  something after the first run, and send me the log of anything that fails.
- **Branch protection is probably not available.** On the free plan, private repositories cannot require
  status checks before merging, so a direct push to `main` is accepted and the checks report afterwards.
  The pipeline still works, and Slack tells you, but it does not stop you. The options are GitHub Pro
  (a small monthly cost, which also enables the protection), making the repository public (not
  suitable here), or accepting the gap and working only through pull requests by habit. Check
  Settings, Rules in the repository to see what your plan allows.
- **The scanners are less complete than the dedicated products.** See ADR 0004. They are a floor, not a
  ceiling, and they will miss problems that data-flow analysis would find.
- **The thresholds were tuned on test data.** The secret scanner may flag something harmless in real code
  or miss something unusual. Tune it in a pull request when that happens.
- **No scan runs on code in `tools`** for the security rules, and tests are exempt. Only application and
  package code is covered.
- **The Slack message was tested only as text.** It has never been delivered to a real Slack workspace.
- **The `cooldown` setting of Dependabot** is a recent feature. If GitHub reports an error in
  `dependabot.yml`, remove those lines first.
- **A new advisory can block unrelated pull requests.** That is the policy you chose. Fix the dependency,
  or accept the risk for up to 90 days in `security/accepted-risks.json` with a written reason.
