# Dependency register

Every library that the code depends on directly has a row here. A library without a row fails
`npm run check`, so adding one always comes with its reasons, in the same pull request. The register
exists to keep the number of libraries small enough for one person to hold in mind, and to answer, for
each one, "what do we do if it disappears?".

How to add a row: say what the library is for, say why writing it by hand was not the better choice
(the honest answer is sometimes "it was, but it was not worth the time"), say what you would do if the
library were abandoned or compromised, and say which part of the code may import it. The architecture
rules enforce the last column for the libraries that matter most (see [boundaries](boundaries.md)).
"Used by" lists the workspaces that declare the library: `root`, `core-api`, `portal-api`, `contracts`.

Rules for the choice of a library, in order:

1. Prefer what Node.js already provides, unless the library removes real, repeated code.
2. Prefer a library that is widely used and actively maintained, with few dependencies of its own.
3. Pin the exact version (the checks enforce it), and let Dependabot propose updates.
4. Never add a library to work around a rule of the architecture checks.

| Package | Used by | What it is for | Why not written by hand | If it is abandoned | Where it may be imported |
|---|---|---|---|---|---|
| `typescript` | root | The compiler that checks types, and the parser that every check in `tools/` uses to read the code. | A type checker is a large program, and the checks rely on its syntax tree. | Stay on the last version. The code is plain TypeScript, so another compiler could replace it. | `tools/` and the type check only. |
| `@types/node` | root | Type definitions for Node.js, so the compiler knows the built-in modules. | Definitions follow every Node release, so keeping them by hand would be endless work. | Pin the last version, or write the few definitions that are used. | Types only: no runtime code. |
| `fastify` | core-api | The web server: routes, hooks, request and response handling, limits and timeouts. | A web server that survives malformed and hostile requests (broken framing, oversized bodies, prototype poisoning, slow clients) is a large, security-sensitive program. The built-in `node:http` module gives only the raw pieces. | Stay on the last version. Only `kernel/http` and the route files know it, so moving to another server means rewriting those. | `kernel/http` and `main.ts` (the network rule enforces it). |
| `fastify-type-provider-zod` | core-api | Connects the zod schemas of a route to Fastify: validation of the input, typed handlers, checking of the answer, and the OpenAPI description. | The glue is a few hundred lines with many corners (error shapes, response serialisation, schema conversion). It is maintained by one person, which is the main risk. | Replace it with our own validator and serialiser functions for Fastify (about a hundred lines); the route definitions do not change. | `kernel/http` and the route files of modules (for the plugin type). |
| `@fastify/swagger` | core-api | Collects the routes into an OpenAPI document (`docs/api/openapi.json`). | Walking Fastify's route table and building the document by hand is possible, and the fallback below does exactly that. | A small script that builds the document from the same route schemas with `z.toJSONSchema`. | `kernel/http` only, and the script that writes the document. |
| `@fastify/helmet` | core-api | Sets the security headers on every answer (content security policy, no sniffing, no framing, and the others). | It could be ten lines in a hook. The library keeps the list of headers and their values current as browsers change. | Write the headers in a hook of our own. | `kernel/http` only. |
| `@fastify/rate-limit` | core-api | Limits how many requests one address can make in a time window. | A counter per address is short, but the corners are not: memory growth, the limit headers, proxies, clean-up. | Replace it with an in-memory limiter of our own (one process, so no shared store is needed). | `kernel/http` only. |
| `pino` | core-api | Writes the logs as JSON lines, fast, with the redaction of sensitive fields. Fastify uses it natively. | Fast, safe structured logging with redaction and child loggers is more than a `JSON.stringify` and a write. | Fastify accepts any logger with the same methods, so a small writer of our own can take its place. | `kernel/logging` only. |
| `pg` | core-api | The PostgreSQL driver: the wire protocol, the connection pool and type conversion. | Speaking the protocol, with authentication, pooling and parameter binding, is not something to rewrite. | Switch to another driver; only `kernel/db` imports it, and the rest of the code sees the `Queryable` interface. | `kernel/db` and, later, the infrastructure layer of a module (the database rule enforces it). Also `tools/db`, the migration runner, which is not application code. |
| `@types/pg` | core-api | Type definitions for `pg`, so the compiler knows its functions. | Definitions follow every release of the driver. | Write the few definitions that are used, or pin the last version. | Types only: no runtime code. |
| `zod` | core-api, contracts | Checks the shape of settings, requests and answers, and gives their TypeScript types. One definition serves for the check, the type and the API description. | Hand-written validation is long, uneven and easy to get wrong, and the types would have to be kept in step by hand. | It is small and has no dependencies of its own; pin the last version. | `kernel/config`, `kernel/http`, route files, and the contracts package. |
| `react` | staff-web | Builds the screens of the staff application from components and keeps them in step with the data. | A user interface library is the core of the front end; rewriting its update logic would be the whole project. | The code uses plain components and hooks. Move to Preact, which accepts the same code, or fork the last version. | `apps/staff-web/src` only. |
| `react-dom` | staff-web | Draws React components in the browser page. | It is the browser half of React and cannot be separated from it. | Follows React: Preact brings its own. | `apps/staff-web/src/main.tsx` and the tests. |
| `react-router` | staff-web | Maps the address in the browser to a page and moves between pages without reloading. | Handling history, links, current-page marking and unknown addresses correctly is subtle, and accessibility depends on it. | Replace it with a small router; the pages are plain components and only `app.tsx` and the layout use it. | `apps/staff-web/src` only. |
| `clsx` | staff-web | Joins class names conditionally. | It is a few lines; it is kept because the button and field components of the shadcn pattern are written against it. | Replace it with a three-line function in `ui/cn.ts`. | `apps/staff-web/src/ui/cn.ts` only. |
| `tailwind-merge` | staff-web | Lets a later Tailwind class win over an earlier conflicting one when classes are combined. | The rules of which Tailwind classes conflict are long and change with Tailwind versions. | Drop it and write classes without overrides; components would lose their override option. | `apps/staff-web/src/ui/cn.ts` only. |
| `class-variance-authority` | staff-web | Describes the variants of a component (primary and secondary button, the tones of an alert) in one table. | Variants can be written with plain objects; this keeps the tables short and typed. | Replace each table with a lookup object; about a dozen lines per component. | `apps/staff-web/src/ui` only. |
| `@radix-ui/react-slot` | staff-web | Lets a component pass its look to the element inside it (a link that looks like a button). | The merging of props and references that makes this correct is easy to get subtly wrong. | Remove the `asChild` option of the button; nothing else uses it. | `apps/staff-web/src/ui/button.tsx` only. |
| `lucide-react` | staff-web | The icons of the interface. | Drawing and keeping consistent a set of accessible icons is work that does not belong in this project. | Replace the three icons used with inline SVG; each is a few lines. | `apps/staff-web/src/ui` only. |
| `vite` | staff-web | Serves the front end during development and builds the files that are published. | A bundler with a development server and hot reload is a large program. | Stay on the last version; the build produces plain files and nothing depends on Vite at run time. | Configuration only (`apps/staff-web/vite.config.ts`). |
| `@vitejs/plugin-react` | staff-web | Teaches Vite to build React code (the JSX syntax and fast refresh in development). | It is the official glue and is small, but its job is specific to React and Vite. | Use the compiler's JSX output with Vite's own settings; slower refresh in development. | `apps/staff-web/vite.config.ts` only. |
| `tailwindcss` | staff-web | Produces the style sheet from the class names used in the code. | A utility class system with a build step that removes the unused ones is its own product. | Write plain CSS; the classes in the components would need translating, which is slow but mechanical. | Used through its style sheet import and `@tailwindcss/vite`; not imported in code. |
| `@tailwindcss/vite` | staff-web | Runs Tailwind inside the Vite build. | It is the official connection and the alternative is a separate build step. | Run the Tailwind command line before the Vite build. | `apps/staff-web/vite.config.ts` only. |
| `vitest` | staff-web | Runs the tests of the front end (component and client tests) in the same setup as the build. | `node:test` cannot compile JSX or run a browser-like page; a test runner for this is a large program. | Move the tests to another runner that understands Vite configuration, such as Jest with a transform. | Test files (`*.spec.ts`, `*.spec.tsx`), the test helpers and `vite.config.ts`. |
| `jsdom` | staff-web | A page, without a browser, in which component tests run. | A browser's document model is far too large to imitate. | Use `happy-dom`, which vitest also supports. | Used by vitest only; not imported in code. |
| `@testing-library/react` | staff-web | Draws a component in a test and finds elements the way a person would (by role and label). | Finding elements by their role keeps the tests honest about what a person can perceive. | Use the plain React test utilities; the tests would be longer and more fragile. | Test files and test helpers only. |
| `@testing-library/user-event` | staff-web | Types and clicks in tests the way a person does, including the events a real browser sends. | A faithful imitation of keyboard and pointer events is long and easy to get wrong. | Use the events of `@testing-library/react`; less realistic. | Test files only. |
| `@types/react` | staff-web | Type definitions for React, so the compiler checks components and hooks. | Definitions follow every React release. | Pin the last version. | Types only: no run-time code. |
| `@types/react-dom` | staff-web | Type definitions for the browser half of React. | Definitions follow every React release. | Pin the last version. | Types only: no run-time code. |
| `i18next` | staff-web | Looks up the text of the screen by key in the chosen language, fills in values and handles plural forms. | A lookup is easy to write; plurals, fallbacks and a standard format for translators are not worth rewriting. | Go back to a small lookup function; the texts stay as they are (they are plain objects). | `apps/staff-web/src/i18n` only. |
| `react-i18next` | staff-web | Connects i18next to React so that components redraw when the language changes. | The subscription logic is easy to get subtly wrong. | Write a small context around `i18next`, about thirty lines. | `apps/staff-web/src/i18n` only. |
| `eslint` | root | Finds mistakes that the compiler and the repository checks do not look for: unused variables, promises nobody waits for, wrong use of React hooks. | A linter that understands the whole language is a very large program. | Remove `npm run lint` from the check; the compiler and `tools/checks` still run. | Run as a program (`npm run lint`); never imported by the code. |
| `@eslint/js` | root | The basic ESLint rule set that the project builds on. | A rule set maintained by the ESLint team is better than a copy kept here. | Same as `eslint`. | `eslint.config.mjs` only. |
| `typescript-eslint` | root | Lets ESLint read TypeScript and use the type information, which enables the rules about promises and unsafe values. | Reading TypeScript and its types is the compiler's job; no hand-made version is realistic. | Same as `eslint`. | `eslint.config.mjs` only. |
| `eslint-plugin-react-hooks` | root | The rules for React hooks (an effect with the wrong dependencies, state set inside an effect). Applied to `apps/staff-web` only. | The rules encode how React works; writing them by hand would risk being wrong. | Delete the entry in `eslint.config.mjs`; the front end tests still run. | `eslint.config.mjs` only. |
| `eslint-config-prettier` | root | Switches off the ESLint rules that argue with Prettier about layout, so the two tools never disagree. | A list of the rules to switch off changes with every ESLint release. | Write the list in `eslint.config.mjs` by hand. | `eslint.config.mjs` only. |
| `prettier` | root | Formats every `.ts` and `.tsx` file the same way, so reviews show real changes and never layout arguments. | Formatting rules are endless to write and agree on. | Remove `npm run format:check` from the check; the code stays as it is. | Run as a program (`npm run format`, `npm run format:check`); never imported by the code. |
| `pino-pretty` | root | Shows the development logs as readable coloured lines instead of JSON. Used only by `npm run dev`. | A formatter that handles every field Pino can write, with colours and time, is long to write and test. | Delete it. `npm run dev` falls back to JSON lines on its own (`tools/dev-pretty.ts`). | `tools/dev.ts` only, as a program it starts; never imported by the applications. |
